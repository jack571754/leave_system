## 二、深度问题分析

### 2.1 【严重】Legacy 角色与 RBAC 双轨并存，存在权限绕过风险

**问题描述**：

`AccessService` 中几乎所有检查方法都包含 Legacy `user.role` 回退逻辑：

```python
# services.py:55 — _is_admin_user
return getattr(user, 'role', None) == getattr(user.Role, 'ADMIN', None)

# services.py:207 — can_submit_task
if getattr(user, 'role', None) == user.Role.ADMIN:
    return task.campaign.is_open()

# services.py:227 — can_approve_task
if getattr(user, 'role', None) == user.Role.ADMIN:
    return True

# services.py:232 — can_view_report
return getattr(user, 'role', None) in [user.Role.ADMIN, ...]
```

**影响**：
- 即使 RBAC 系统中已撤销某用户的 admin 角色分配，只要 `user.role` 字段仍为 `admin`，该用户依然拥有全部管理权限
- `get_user_role_codes` 方法始终将 Legacy `user.role` 合入角色集合（第80行），意味着任何 Legacy 角色在 RBAC 角色检查中都生效
- `can_submit_task`、`can_approve_task`、`can_withdraw_task` 等方法绕过 RBAC 直接检查 Legacy role，RBAC deny 规则对 Legacy admin 无效

**建议**：
1. 设定 Legacy 迁移截止时间表，在迁移完成后移除所有 Legacy fallback 代码
2. 在过渡期内，将 Legacy 角色检查统一收拢到 `get_user_role_codes` 一处，其他方法不再直接检查 `user.role`
3. 为 User 模型添加 `role_source` 字段标识（`legacy` / `rbac`），允许管理员选择生效来源

---

### 2.2 【严重】N+1 查询与性能瓶颈

**问题描述**：

`AccessService` 中多个方法存在严重的查询性能问题：

**(a) `get_authorized_store_ids` — 每次请求 5-7 次数据库查询**

```python
# services.py:253-261 — 4 次独立查询
store_ids.update(Store.objects.filter(owner=user, ...).values_list('id', flat=True))
store_ids.update(StoreMembership.objects.filter(user=user, ...).values_list('store_id', flat=True))
store_ids.update(PlanTask.objects.filter(Q(assignee=user) | ...).values_list('store_id', flat=True))
store_ids.update(TaskApprovalInstance.objects.filter(...).values_list('task__store_id', flat=True))
```

加上后续 `_matching_data_configs` 和 `_matching_data_scope_rules` 的循环查询，单个用户一次权限检查可达 **10+ 次数据库查询**。

**(b) `get_visible_pages` — N+1 问题**

```python
# services.py:65-66 — 对每个 page 调用 can_access_page，每次重新查询数据库
pages = FrontendPagePermission.objects.filter(is_active=True).order_by(...)
return [page for page in pages if self.can_access_page(user, page.page_key)]
```

`can_access_page` 内部调用 `get_user_role_codes`，每个页面权限检查都会重新执行完整的角色查询链。10 个页面 = **10 次角色查询**。

**(c) `_descendant_org_unit_ids` — BFS 逐层查询**

```python
# services.py:337-347 — 每层一次查询
child_ids = list(OrgUnit.objects.filter(parent_id=current).values_list('id', flat=True))
```

如果组织树深度为 N，则执行 N 次查询。

**(d) `_matching_data_configs` / `_matching_data_scope_rules` — 循环内查询**

```python
# services.py:281-285 — 遍历所有 config，每个执行 filter().exists()
for config in configs:
    if config.subject_type == ... and config.target_users.filter(pk=user.pk).exists():
        matched.append(config)
```

**影响**：`permission_navigation` context processor 在**每个请求**中都被调用，上述查询链在每次页面加载时全部执行。在高并发场景下，这将成为严重瓶颈。

**建议**：
1. 为 `get_user_role_codes` 添加请求级缓存（使用 `request._rbac_role_cache`）
2. 使用 `__in` 批量查询替代 `_matching_data_configs` 中的循环 `filter().exists()`
3. 将 `get_authorized_store_ids` 改为单条 SQL UNION 查询
4. `get_visible_pages` 应先一次性获取角色和权限集合，再遍历页面
5. `_descendant_org_unit_ids` 改用 CTE 递归或预构建 MPTT 物化路径

### 2.3 【中等】权限模型冗余 — DataPermissionConfig 与 DataScopeRule 重叠

**问题描述**：

`DataPermissionConfig` 和 `DataScopeRule` 两个模型功能高度重叠：

| 特性 | DataPermissionConfig | DataScopeRule |
|------|---------------------|---------------|
| 按用户匹配 | `target_users` M2M | `target_users` M2M |
| 按角色匹配 | `target_roles` JSONField | `target_roles` M2M (正确) |
| Store 级范围 | 支持 | 支持 |
| OrgUnit 级范围 | 支持 | 支持 |
| ALL 级范围 | 支持 | 支持 |
| Self/Subordinate/Assigned | **不支持** | 支持 |
| conditions 字段 | **无** | JSONField |

关键问题：
- `DataPermissionConfig.target_roles` 使用 JSONField 存储角色 code 列表，与 `DataScopeRule.target_roles` 使用 M2M 关联不一致
- `AccessService._expand_store_scope` 中使用 `in` 集合比较同时处理两个模型的 `ScopeType` 枚举，逻辑混乱
- 两个模型的匹配逻辑（`_matching_data_configs` 和 `_matching_data_scope_rules`）几乎相同

**建议**：
1. 废弃 `DataPermissionConfig`，将其功能合并到 `DataScopeRule`
2. 将 `DataPermissionConfig.target_roles` 的 JSONField 改为 M2M（统一到 DataScopeRule 的方案）
3. 在 `DataScopeRule` 上添加迁移字段以覆盖 `DataPermissionConfig` 的全部用例

---

### 2.4 【中等】Department 与 OrgUnit 双组织体系并存

**问题描述**：

系统同时存在两套组织架构模型：

- **Department**：Legacy 部门模型，被 `User.department`、`ApprovalFlow.department`、`SalesPlan.department` 引用
- **OrgUnit**：新组织单元模型（部门/小组/平台三级），被 `Store.org_unit`、`PlanCampaign.org_unit`、`PlanTask.org_unit` 引用

用户同时拥有 `department` 和 `org_unit` 两个外键，审批流程和计划提报分别使用不同的组织关联。

**影响**：
- 数据一致性风险：用户可能被分配到 Department A 但 OrgUnit B，导致审批链路断裂
- 新功能开发时需要同时考虑两套体系，增加复杂度
- 权限判定时 `get_user_role_codes` 的 scope 解析逻辑（第96-97行）需要在 department 和 org_unit 之间做假设

**建议**：
1. 制定统一组织模型方案，将 Department 的职责迁移到 OrgUnit
2. 在 OrgUnit 中明确 support 全层级：`department → group → platform`
3. 迁移完成后删除 Department 模型及所有外键引用

### 2.5 【中等】权限中心页面为只读展示，缺少管理功能

**问题描述**：

`permission_center` 视图（`permissions/views.py`）仅渲染统计数据和列表展示：

```python
# views.py — 只有 center 和 no_access 两个视图
path('', views.permission_center, name='center'),
path('no-access/', views.no_access, name='no_access'),
```

当前无法在权限中心页面完成以下操作：
- 创建/编辑/删除角色
- 分配/撤销用户角色
- 配置角色权限
- 管理数据范围规则
- 管理前端页面权限

所有管理操作目前只能通过 Django Admin 后台（unfold）完成。

**影响**：非技术管理员（如业务主管）无法自行管理权限，必须依赖系统管理员通过 Admin 后台操作。

**建议**：
1. 在权限中心添加角色管理 CRUD 视图
2. 添加用户角色分配/撤销界面（支持拖拽或搜索选择）
3. 添加数据范围规则的图形化配置界面
4. 添加操作审计日志（谁在什么时间修改了什么权限）

### 2.6 【中等】`@page_access_required` 装饰器缺少 HTMX 支持

**问题描述**：

```python
# decorators.py — 无条件 redirect 到 no_access 页面
def _wrapped(request, *args, **kwargs):
    if permissions_service.can_access_page(request.user, page_key):
        return view_func(request, *args, **kwargs)
    messages.error(request, 'You do not have access to this page.')
    return redirect('permissions:no_access')
```

HTMX 请求被拦截时返回 302 重定向，HTMX 客户端会跟随重定向到 `no_access` 页面，但这不是理想的 HTMX 交互模式。

**建议**：
1. 对 HTMX 请求返回 HTTP 403 + HTML 片段（而非 302 重定向）
2. 或返回 `HX-Redirect` 响应头让 HTMX 客户端做页面级跳转
3. 添加 `HX-Trigger` 头部触发前端 toast 提示

### 2.7 【低等】`_permissions_schema_ready` 在每次请求中执行数据库内省

**问题描述**：

```python
# services.py:349-354
def _permissions_schema_ready(self):
    try:
        table_names = set(connection.introspection.table_names())
    except (OperationalError, ProgrammingError):
        return False
    return self.PERMISSIONS_TABLES.issubset(table_names)
```

此方法在几乎每个 AccessService 方法中被调用，且每次都执行数据库内省（`connection.introspection.table_names()`）。这在生产环境中是完全不必要的——一旦迁移完成，表结构不会变化。

**影响**：每次权限检查增加一次数据库元数据查询。

**建议**：
1. 使用 `@lru_cache` 或模块级变量缓存结果（在进程生命周期内只需检查一次）
2. 在 `post_migrate` signal 中重置缓存
3. 或使用 `AppConfig.ready()` 中设置标志位

---

### 2.8 【低等】User 模型缺少字段验证和约束

**问题描述**：

**(a) `User.phone` 无格式验证**

```python
phone = models.CharField('手机号', max_length=20, blank=True)
```

无正则校验，可输入任意字符串。

**(b) `User.manager` 无循环引用保护**

`manager` 是指向自身的 ForeignKey，没有数据库层或应用层的循环引用检测。

**(c) `profile_view` 无输入验证**

```python
# users/views.py:11-16 — 直接赋值无任何验证
user.first_name = request.POST.get('first_name', '')
user.email = request.POST.get('email', '')
user.phone = request.POST.get('phone', '')
user.save()
```

缺少表单验证，用户可提交超长字符串或非法格式。

**建议**：
1. 为 `phone` 字段添加 `validators=[RegexValidator(regex=r'^1[3-9]\d{9}$')]`
2. 为 `email` 使用 Django Form 或 ModelForm 验证
3. 添加 `clean_manager` 方法防止循环引用
4. 将 `profile_view` 改用 Django Form/ModelForm

---

### 2.9 【低等】FrontendPagePermission 的 `allowed_roles` 使用 JSONField 而非 M2M

**问题描述**：

```python
# models.py:187
allowed_roles = models.JSONField(default=list, blank=True)
```

使用 JSONField 存储角色 code 列表（如 `['admin', 'manager']`），存在以下问题：
- 无外键约束，角色被删除后 JSON 中的 code 成为悬挂引用
- 无法使用 ORM 进行 JOIN 查询
- 数据一致性依赖应用层保证

**建议**：
1. 改为 `ManyToManyField(Role, ...)` 关联
2. 迁移时将 JSON 数据转换为 M2M 记录
3. 同步修改 `can_access_page` 中的匹配逻辑

---

### 2.10 【低等】UserRoleAssignment 缺少唯一约束和冲突处理

**问题描述**：

同一用户可以被分配相同角色多次（不同 scope），但没有唯一约束防止完全重复的分配：

```python
# 可以创建两条完全相同的记录（user=1, role=1, scope_type='global'）
UserRoleAssignment.objects.create(user=user, role=role, scope_type='global')
UserRoleAssignment.objects.create(user=user, role=role, scope_type='global')
```

`get_user_role_codes` 只关心 role code 集合，重复不影响结果，但会导致：
- Admin 界面显示混乱
- 不必要的数据冗余

**建议**：
1. 添加 `unique_together = ['user', 'role', 'scope_type', 'org_unit', 'store']`
2. 或在 Admin 中添加 `clean` 方法去重
3. 添加数据清理脚本移除已有重复记录

## 六、总结

当前权限用户管理系统**架构设计合理**，RBAC 体系覆盖了页面级、数据级和操作级三个维度，Legacy 兼容层保证了平滑过渡。但存在三个核心问题需要优先解决：

1. **安全**：Legacy fallback 导致 RBAC deny 规则可被绕过
2. **性能**：权限检查的 N+1 查询问题在高并发下将成为瓶颈
3. **治理**：模型冗余和组织体系双轨增加了维护成本

建议按 Phase 1-4 路线图逐步优化，优先解决安全问题和性能瓶颈。
