## 1. 产品概述 (Product Overview)

- **产品定位**：基于 Frappe + Vue 3 的门店商品销售规划与审批平台，兼具业务操作前台与权限/组织/规则配置后台，适用于企业内部的销售计划填报、审核、分析与协同管理。
- **核心价值**：
  1. 将总部下发的计划任务按门店维度拆解，形成可执行的商品计划填报工作台。
  2. 通过逐级审批、退回、撤回、催办，约束计划提报流程，降低口径不一致和漏填风险。
  3. 通过机制管理、透视分析、导入导出与权限隔离，提高计划编制效率和管理可控性。
  4. 通过飞书登录、飞书通知等集成，降低系统接入和组织协同成本。
- **产品形态**：
  1. 前台业务层：`PlanningDashboard`、`StoreDetail`、`ApprovalCenter`、`MechanismManagement`、`DataAnalysis`、`NoAccess`。
  2. 后台配置层：Frappe DocType 管理页，负责计划任务、门店主数据、审批实例、规则机制、权限配置、页面权限配置、组织结构等。

## 2. 用户角色与权限 (User Roles & Permissions)

| 角色 | 权限范围 | 核心使用场景 |
|---|---|---|
| Administrator | 全量数据与全量操作权限；可跳过多数业务限制 | 系统初始化、全局排错、紧急代操作 |
| System Manager | 全量门店可见、全量页面可见、配置类 DocType 完整维护权限 | 系统配置、权限维护、任务配置、审批管理 |
| Approver | 可访问审批中心；对当前步骤属于自己的审批实例执行通过/驳回 | 审批待办处理 |
| Store Manager | 可访问审批中心、数据分析；通常可查看与自身相关门店和任务 | 门店负责人或业务主管查看填报与审批进展 |
| Mechanism Manager | 可访问机制管理页；维护产品机制及产品组合 | 促销/活动机制配置 |
| Data Analyst | 可访问数据分析页；进行透视分析、导出结果 | 经营分析、复盘、横向对比 |
| 计划管理类自定义角色 | 对 `Store List` 等主数据具备读写/导入能力 | 计划管理员维护门店主数据与运营范围 |
| 门店负责人 | 可在门店详情页录入计划、导入商品、提交审批、在特定状态下撤回或继续修改 | 门店计划填报执行 |
| 普通登录用户 | 仅可访问被页面权限和门店数据权限共同授权的内容 | 被授权查看特定页面或特定门店数据 |

### 2.1 权限规则拆解

- **页面权限**：前端路由通过 `get_page_permissions` 返回的页面配置控制；支持“所有用户可访问”或“按角色访问”两种模式。
- **数据权限**：`Store List` 可见范围来自四类并集：
  1. 用户是门店负责人。
  2. `Permission Config` 授权。
  3. `User Permission` 授权。
  4. 用户曾作为提交人提交且已审批通过的历史门店。
- **操作权限**：
  1. 编辑计划要求任务处于“开启中”且在填报时间窗口内。
  2. 提交审批原则上要求当前用户是门店负责人；`Administrator` 可例外。
  3. 审批实例存在后，是否还能编辑取决于审批状态与提交人身份。
  4. 撤回仅允许提交人对待审实例执行。
  5. 审批通过/驳回仅允许当前步骤审批人执行。

## 4. 核心功能需求 (Core Functional Requirements)

### 4.1 模块名称：计划任务创建与分发

- **用户故事**：作为系统管理员，我希望创建不同类型的计划任务并指定适用门店，以便统一组织门店在规定时间内完成计划填报。
- **业务逻辑**：
  1. 任务必须定义计划类型、开始日期、结束日期。
  2. 任务默认状态为“开启中”，关闭后不允许继续提交审批或审批处理。
  3. 门店分配支持手工添加、按平台覆盖、按部门覆盖。
  4. 任务下的门店以 `Tasks Store` 子表记录，并记录提交状态、审批状态、当前步骤、待审批人。
- **前置/后置条件**：
  1. 前置：管理员具备任务配置权限。
  2. 后置：任务生成后进入看板与筛选器，可作为门店填报和审批的作用域。

### 4.2 模块名称：门店商品计划录入与保存

- **用户故事**：作为门店负责人，我希望在门店详情页维护商品及各月份计划数量，以便完成本门店销售计划提报。
- **业务逻辑**：
  1. 录入入口包含新增商品、导入模板、表格编辑三种方式。
  2. 商品计划以 `Commodity Schedule` 保存，关键维度为任务、门店、商品、日期、数量。
  3. 页面存在自动保存与保存状态反馈。
  4. 支持批量删除选中商品计划，支持导出当前门店计划。
  5. 若审批已提交且状态不允许编辑，则页面进入只读或部分禁用。
- **前置/后置条件**：
  1. 前置：用户对门店有数据权限；任务处于开启且在可编辑窗口内。
  2. 后置：计划数据写入商品计划表，并可进入审批流或分析流程。

### 4.3 模块名称：审批提交流转

- **用户故事**：作为门店负责人，我希望提交门店计划进入审批；作为审批人，我希望按步骤处理审批，以便完成计划审核闭环。
- **业务逻辑**：
  1. 提交审批前校验任务状态必须为“开启中”。
  2. 提交审批前校验当前时间仍在填报期限内。
  3. 原则上只有门店负责人可提交审批；管理员可特批提交。
  4. 提交后创建或重建 `Approval Instance`，并返回审批链。
  5. 审批动作支持 `approve`、`reject_to_previous`、`reject_to_submitter`、`withdraw`。
  6. 审批历史独立记录，保留审批人、动作、意见、时间。
  7. 当状态为“待审批”时，提交人通常不可再编辑；当状态为“已驳回”或“已撤回”且提交人为当前用户时，可重新编辑和提交。
- **前置/后置条件**：
  1. 前置：门店已有可提交计划数据，且审批链可解析。
  2. 后置：门店任务的审批状态、当前步骤、待审批人被同步回 `Tasks Store`，驱动看板和审批中心展示。

### 4.4 模块名称：审批中心处理

- **用户故事**：作为审批人，我希望集中查看待我审批、我已审批、我提交的记录，并支持批量处理，以便提升处理效率。
- **业务逻辑**：
  1. “待我审批”并非简单按状态筛选，而是要判断当前用户是否恰好是审批链当前步骤审批人。
  2. “我已审批”来源于审批历史表中当前用户执行过通过/驳回动作的实例。
  3. “我提交的”来源于当前用户为提交人的审批实例，且排除未开始状态。
  4. 批量审批基于审批实例 ID 列表逐条执行。
- **前置/后置条件**：
  1. 前置：用户具备审批中心页面权限。
  2. 后置：统计卡、列表、审批状态同步更新。

### 4.5 模块名称：机制规则应用

- **用户故事**：作为机制管理人员，我希望维护促销机制及其商品组合，并将其应用到计划数据中，以便统一活动口径与商品方案。
- **业务逻辑**：
  1. 机制按类别管理，支持启停状态。
  2. 每个机制由主表与子表构成，子表记录商品、数量、赠品等信息。
  3. 前端机制页主要承担检索、统计、详情查看；新增和编辑通过 Frappe 后台页面完成。
  4. 后端提供机制应用接口，说明机制并非只读档案，而是可对业务数据产生影响。
- **前置/后置条件**：
  1. 前置：机制已配置且处于有效状态。
  2. 后置：推断功能，机制可作为门店计划或活动组合填报的参考/套用来源。

### 4.6 模块名称：数据分析与透视分析

- **用户故事**：作为数据分析人员，我希望按门店、任务、审批状态、月份等维度拖拽分析计划数据，并导出结果，以便进行经营分析和复盘。
- **业务逻辑**：
  1. 系统支持常规分析接口、透视分析接口和 ClickHouse 快速分析接口。
  2. 透视页支持行列值布局拖拽、过滤条件映射、默认布局恢复、结果导出。
  3. 分析页明确强调“服务端聚合”，说明权限隔离与性能优化在后端完成。
  4. 门店计划页还支持规则引擎驱动的“一键异常分析”。
- **前置/后置条件**：
  1. 前置：用户具备分析页权限，且对相应门店/任务有数据访问权。
  2. 后置：输出聚合表、查询耗时、导出文件或异常清单。

### 4.7 模块名称：权限与页面可见性管理

- **用户故事**：作为系统管理员，我希望按用户/角色/组织范围控制数据与页面访问，以便实现严格的数据隔离和职责分层。
- **业务逻辑**：
  1. `Permission Config` 支持按用户或按角色配置。
  2. 授权范围支持门店级、平台级、部门级，最终统一落到授权门店列表。
  3. `Frontend Page Permission` 支持页面路径、图标、菜单顺序、是否登录、是否全员可访问、允许角色等配置。
  4. 页面权限与门店数据权限相互独立，前者决定“能否进页面”，后者决定“进来后能看哪些数据”。
- **前置/后置条件**：
  1. 前置：管理员维护好组织、门店、角色、页面注册信息。
  2. 后置：前端菜单、路由访问、门店列表和查询结果按配置动态变化。

## 5. 核心业务流程 (Core Business Flows)

### 5.1 流程一：计划任务下发到门店填报再到审批完成

1. 系统管理员创建计划任务，设置计划类型、起止时间和门店范围。
2. 系统在任务下生成门店任务子记录，每个门店初始为“未开始/未提交”。
3. 门店负责人登录看板，只能看到自己有权限且属于当前任务范围的门店。
4. 门店负责人进入门店详情页，通过新增、导入或表格编辑维护商品计划。
5. 系统自动保存或批量保存商品计划，并实时显示保存状态。
6. 门店负责人点击“提交审批”，系统校验任务状态、时间窗口、门店负责人身份。
7. 校验通过后系统创建审批实例，生成审批链，并把门店任务状态同步为待审批。
8. 当前步骤审批人在审批中心看到“待我审批”记录，可查看详情并执行通过或驳回。
9. 若通过，审批流进入下一步；若到达最后一步，则审批实例状态改为“已通过”。
10. 若驳回到上一步或提交人，则门店任务重新回到可编辑阶段；提交人可修改后再次提交。
11. 审批结果同步反映到看板、门店详情与审批中心。

### 5.2 流程二：门店计划录入到分析与导出

1. 门店负责人或分析用户进入门店详情页或数据分析页。
2. 门店详情页可对当前商品计划执行异常分析，识别异常商品和预警项。
3. 数据分析页通过筛选条件限定任务、门店、审批状态、月份等范围。
4. 用户拖拽行、列、值字段，系统调用服务端聚合接口返回透视结果。
5. 用户可刷新、重置布局、恢复默认布局，并导出当前分析结果。
6. 推断功能：分析结果可用于复盘门店执行情况、机制效果和审批后计划差异。

## 6. 数据实体与关系 (Data Models & Entities)

| 实体 | 核心字段 | 说明 |
|---|---|---|
| Schedule Tasks | `name`、`type`、`type_name`、`status`、`start_date`、`end_date`、`set_store` | 计划任务主表，定义任务类型、时间范围和门店分配 |
| Tasks Store | `store_id`、`store_owner`、`status`、`approval_status`、`current_step`、`pending_approver` | 任务下的门店子记录，承载门店级提交与审批状态 |
| Store List | `external_shop_id`、`shop_name`、`shop_type`、`channel`、`department`、`planning_officer`、`store_owner` | 门店主数据，既是组织维度，也是权限与审批的核心对象 |
| Commodity Schedule | `task_id`、`store_id`、`code`、`quantity`、`sub_date` | 门店商品计划明细，记录商品在任务和日期维度下的数量 |
| Product List | 商品编码、名称等 | 商品主数据，作为计划填报与机制配置的商品基础档案 |
| Approval Instance | `task_id`、`store_id`、`current_step`、`status`、`submitter`、`round` | 审批实例主表，一个门店在一个任务下可有多轮审批 |
| Approval History | `approval_instance`、`step_order`、`approver`、`action`、`comments`、`action_time` | 审批历史流水，记录逐步审批动作 |
| Product Mechanism | `mechanism_name`、`category`、`is_active`、`content_summary` | 机制主表，定义活动/机制的总体信息 |
| Product Mechanism Item | 商品编码、数量、赠品标识等 | 机制子表，记录机制下的商品组合 |
| Department | 部门标识、部门名称 | 组织维度，用于门店归属与权限范围配置 |
| Platform | 平台标识、平台名称 | 平台维度，用于门店归属与权限范围配置 |
| Permission Config | `config_name`、`config_mode`、`scope_type`、`target_users/roles`、`scope_stores` | 数据权限配置主表，支持按用户/角色与按门店/平台/部门授权 |
| Frontend Page Permission | `page_name`、`page_label`、`page_path`、`show_in_menu`、`require_auth`、`allow_all_users` | 页面级权限配置主表 |
| Frontend Page Permission Role | 角色列表 | 页面允许访问角色子表 |
| Reminder Log | 催办或提醒相关字段 | 记录提醒触达行为 |
| Social Login Key / 飞书配置 | `client_id`、`client_secret` 等 | 第三方登录配置载体 |

### 6.1 实体关系说明

- 一个 `Schedule Tasks` 对应多个 `Tasks Store`。
- 一个 `Tasks Store` 对应一个门店在一个任务下的状态切片。
- 一个门店在一个任务下可拥有多条 `Commodity Schedule`。
- 一个门店在一个任务下可产生一个或多轮 `Approval Instance`。
- 一个 `Approval Instance` 对应多条 `Approval History`。
- 一个 `Product Mechanism` 对应多条 `Product Mechanism Item`。
- `Permission Config` 通过用户/角色与门店范围建立数据授权映射。
- `Frontend Page Permission` 通过角色子表建立页面访问控制。
- `Store List` 同时连接组织维度、权限维度、审批维度和业务填报维度，是全系统核心主数据。

## 7. 非功能性需求推断 (Non-Functional Requirements)

### 7.1 安全性

1. 基于 Frappe 会话与白名单方法控制接口访问。
2. 页面权限与数据权限分层控制，避免仅靠前端隐藏菜单。
3. 飞书 OAuth 登录通过授权码换取用户信息，并将用户与内部账号关联。
4. 存在 `request_page_access` 流程，说明系统支持权限申请与管理员通知。

### 7.2 性能要求

1. 看板和分析接口在后端执行过滤与聚合，减少前端数据处理压力。
2. 前端权限、页面权限存在 sessionStorage 缓存。
3. 数据分析提供 ClickHouse 快速接口，表明系统已针对大数据量分析做性能分层。
4. 商品计划、审批状态变更后会触发缓存失效，说明系统存在结果缓存。

### 7.3 可靠性

1. 使用事务装饰器处理审批等关键写操作。
2. 审批状态会同步回门店任务子表，降低主流程展示和审批实例之间的不一致风险。
3. 定时任务自动关闭过期任务，防止长期悬挂。

### 7.4 可审计性

1. 审批历史完整留痕。
2. DocType 开启 `track_changes` 的较多，说明系统重视操作追踪。

### 7.5 可扩展性

1. 计划类型、页面权限、权限范围类型、机制分类均采用配置化字段，便于扩展。
2. 组织、审批、权限、机制均拆成独立 API 与服务层，扩展业务域较容易。

### 7.6 第三方集成

1. 飞书登录：OAuth 授权、自动建用户、登录后跳转指定业务页。
2. 飞书通知：支持任务通知、审批催办、Webhook/连接测试。
3. 推断功能：具备进一步对接企业通讯录、消息中心、组织同步的潜力。

### 7.7 推断功能

1. 登录外围可能还会包含统一登录入口、登录后跳转管理、异常页兜底。
2. 若系统对外推广为企业内部 SaaS，后续通常会补齐注册关闭、账号启停、权限申请审批等标准能力；但这些在当前源码中仅有局部证据，不应视为既成核心功能。
